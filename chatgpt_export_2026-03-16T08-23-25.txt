Yes. You cannot fully stop users from installing scam APKs on Android, but you can reduce it a lot from both the user side and the developer/product side.

My opinion: the biggest mistake is thinking this is only a “user education” problem. It is also a product design and distribution trust problem.

What you can realistically do
1. Make it hard for users to ever need an APK

The safest path is still:

distribute through Google Play

avoid sending APK files over WhatsApp, Telegram, email, or random websites

avoid “please install this update manually” flows

Google says Play Protect scans apps from Play before download, and also checks apps from other sources for potentially harmful behavior. It can warn users, and in some cases deactivate or remove harmful apps. 
Google Help
+1

So if you are building an app, the first prevention layer is simple:

publish on Play Store

push updates through Play

tell users clearly: “We never send APKs by chat.”

That one sentence alone is powerful.

2. Add anti-fraud messaging inside your product

Users get tricked because the attacker creates urgency:
“Your account will be suspended.”
“Install this security update now.”
“Install this trading plugin.”

You should proactively show trust rules in-app and on your site:

“We only distribute via Google Play.”

“We never ask you to install APKs from WhatsApp/Telegram.”

“We never ask for screen sharing, accessibility permission, or device admin through chat support.”

“Any install link must be from our official domain or Play Store listing.”

This sounds basic, but repetition matters.

3. Detect fake or tampered installs on your backend

If you are the app developer, use Play Integrity API.

Google’s official docs say Play Integrity helps verify that requests come from your genuine app, installed by Google Play, running on a genuine/certified Android device, and helps detect tampered app versions or risky environments.

Why this matters

Even if a scammer clones your APK or repackages it:

your server can check whether the app was really installed by Google Play

you can block sensitive actions if integrity fails

you can step up verification for risky sessions

Good pattern

For sensitive actions like:

login

password reset

payout / withdrawal

bank account change

API key creation

device binding

do this:

app requests Play Integrity token

backend verifies it

backend decides risk level

allow, challenge, or block

Example policy

High trust: allow normal use

Medium trust: require OTP / re-auth

Low trust: block withdrawals, block credential changes, show warning

That is much better than “all or nothing.”

4. Bind accounts to trusted devices

A lot of scam APK damage happens because once installed, the attacker takes over a session.

Reduce blast radius:

bind account to known device fingerprint

require re-verification for new device

require confirmation for risky changes

send instant alerts for:

new login

new device

password change

payout address change

API key creation

If you run trading or financial software, this is not optional.

5. Be very careful with Android permissions

Scam APKs often abuse high-risk permissions or flows such as:

Accessibility access

Notification access

Device admin

Screen overlay / draw over other apps

Unknown app install permission

SMS read/receive

Media projection / screen capture

As a legitimate developer, do two things:

request as few dangerous permissions as possible

clearly explain why each permission is needed, in plain language

That helps users spot fake apps later. If your real app never asks for Accessibility, then a fake app asking for it becomes suspicious.

6. Add out-of-band verification for critical actions

Never trust the app alone for very sensitive actions.

Examples:

confirm withdrawals by email or another device

confirm bank/wallet changes with extra approval

delay high-risk actions for a cooling-off period

require re-auth for large transactions

This reduces damage even if a user installs something malicious.

7. Verify your developer identity and branding

Android has a developer verification program intended to help protect users from malware and scams by verifying developer identities. 
Android Developers

Also make your trust signals consistent:

same company name everywhere

same logo everywhere

official domain clearly shown

support staff never send install files directly

help center page: “How to safely install our app”

Scammers win when branding is messy.

8. Protect your website and download pages

If you offer APKs outside Play for enterprise or direct distribution, then you need a much stronger trust model.

At minimum:

serve only over HTTPS

host on your official domain

publish SHA-256 checksums

sign releases consistently

provide clear install instructions

warn users never to trust third-party mirrors

But honestly, for consumer apps, direct APK distribution increases risk a lot. I would avoid it unless there is a strong business reason.

9. Educate users on one concrete Android setting

For users themselves, tell them to keep Google Play Protect on. Google says it is on by default and recommends keeping it enabled. It also suggests enabling improved harmful app detection, especially for apps from outside Play. 
Google Help
+1

Also, Android lets users enable installation from “unknown apps” for specific apps like browsers or messaging apps. That is one of the main paths scammers exploit. 
Google Help
+1

So your user-facing advice can be:

keep Play Protect enabled

do not allow Chrome/WhatsApp/Telegram to install unknown apps unless absolutely necessary

never install APKs from chat links

check whether the app came from Google Play

10. Build fraud monitoring, not just app security

This is the part many programmers skip.

Even if you have a secure app, you still need backend detection for:

unusual device changes

impossible travel

sudden permission-risk patterns

new payout destination

many failed OTP attempts

abnormal order/trading behavior

session token reuse from unusual environments

If the app is in fintech, crypto, trading, banking, wallet, or admin tooling, backend fraud controls matter more than APK hardening alone.

Practical strategy for you as a programmer

If I were designing this today, I would do this stack:

Baseline

Google Play distribution only

Play Protect guidance in help center

strong code signing and release process

no APK sharing by staff, ever

App-side

minimal permissions

clear security messaging

device binding

session hardening

force update through official channel only

Backend

Play Integrity API verification

risk engine for login and critical actions

step-up authentication for suspicious sessions

alerts for new device / payout / password changes

rate limits and anomaly detection

Operations

official security page

anti-scam FAQ screenshots

support scripts that explicitly say “we never send APK files”

abuse reporting channel for fake app links

Very honest answer

If your question is:

“Can we completely prevent users from being tricked into installing scam APKs?”

No.

If your question is:

“Can we reduce successful scams a lot with proper product/security design?”

Absolutely yes.

And for many businesses, the most effective combo is:

official Play distribution + Play Integrity checks + strong backend risk controls + repeated anti-scam messaging

That is the practical answer.

Yes — but only partially on normal Android phones.

My strong view: you cannot build a normal consumer app that fully prevents APK scam installs system-wide on every Android device. Android does not let an ordinary app act like the OS and block all installs from other apps. Android already reserves a lot of that control for the system, Google Play Protect, or device-management / enterprise controls.

What you can build depends on the model.

1. Consumer protection app: possible, but mostly warn/detect

A normal Play Store app can help by:

checking whether Play Protect is on

educating users when they open suspicious links

detecting risky states on the device and warning

protecting your own app/account from risky devices

screening SMS/chat/browser links before users tap through

flagging apps that request suspicious permissions after install

But it usually cannot silently stop another installer app from installing an APK on an unmanaged personal phone. Android requires the user to explicitly opt in to installing unknown apps from a source, and that control is handled by Android, not by your app.

+1

So for regular users, your app is more like:

risk detector

warning system

policy coach

recovery assistant

—not a guaranteed blocker.

2. Enterprise / managed-device app: yes, much stronger

If the phone is a managed device — company-owned, kiosk, MDM, device-owner, or work-profile controlled — then you can build a Device Policy Controller–style app or integrate with enterprise management. Android Enterprise supports policies to:

block unknown-source installs

block them globally in some managed scenarios

control which apps can be installed

prevent disabling Play Protect in managed environments

That is the version where “prevent” becomes much more real.

3. The best product idea: scam-prevention companion app

If you are thinking like a programmer, I would not pitch it as “block all scam APKs.” That promise is too strong.

I would build it as:

“Android Scam Shield”

Core functions:

A. Pre-install warning layer

scan URLs from SMS / WhatsApp / Telegram share intents

detect keywords like “update manually”, “KYC APK”, “bank secure app”, “trading helper apk”

warn if link is not Play Store / official domain

B. Device risk audit

check whether Play Protect is enabled

check whether install-from-unknown-sources is enabled for Chrome / browser / file manager

check accessibility abuse risk exposure conceptually and guide user to review settings

check notification listener / overlay heavy apps and prompt review

Google documents that Play Protect scans apps, warns users, may disable harmful apps, and can remove harmful apps automatically in some cases. Play Integrity also exposes verdicts such as POSSIBLE_RISK, MEDIUM_RISK, and HIGH_RISK tied to Play Protect state and harmful app findings. 
Google Help
+1

C. App reputation and install guidance

paste APK link → app tells user: “Not from Play Store, high risk”

compare package name against your maintained allowlist / reputation service

fetch official publisher info from your backend

D. Post-install incident response

if user already installed something suspicious:

guide them to uninstall

revoke permissions

review accessibility / notification access / overlays

change passwords

resecure banking / wallet / exchange apps

E. Protect your own product
If you own the app being targeted, use Play Integrity API to assess device/app risk and block sensitive actions when the environment looks unsafe.

That is a real, buildable product.

4. What your app cannot reliably do

On a standard non-rooted consumer Android phone, your app generally cannot:

intercept and block every APK install globally

uninstall other apps automatically at will

silently revoke every dangerous permission from other apps

read everything happening inside WhatsApp/Telegram/private apps

act as a full antivirus with OS-level privileges

That is why Google Play Protect exists at the platform/ecosystem layer.

7.1 Installed app detection

class AndroidAppDiscoveryGateway(
    private val context: Context
) : AppDiscoveryGateway {

    override fun isInstalled(packageName: String): Boolean {
        return try {
            context.packageManager.getPackageInfo(packageName, 0)
            true
        } catch (_: Exception) {
            false
        }
    }
}

On Android 11+ this works only for packages visible to your app, which is why the <queries> list matters.

7.2 Open “Install unknown apps” page
Kotlin
class AndroidSettingsNavigator(
    private val context: Context
) : SettingsNavigator {

    override fun openUnknownAppsSettings(packageName: String) {
        val intent = Intent(
            Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES,
            Uri.parse("package:$packageName")
        ).apply {
            addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
        }
        context.startActivity(intent)
    }

    override fun openPlayProtectInstructions() {
        val intent = Intent(Intent.ACTION_VIEW).apply {
            data = Uri.parse("https://support.google.com/googleplay/answer/2812853")
            addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
        }
        context.startActivity(intent)
    }
}

7. Platform integration spec
7.1 Installed app detection

Use PackageManager safely with exception handling.

Kotlin
class AndroidAppDiscoveryGateway(
    private val context: Context
) : AppDiscoveryGateway {

    override fun isInstalled(packageName: String): Boolean {
        return try {
            context.packageManager.getPackageInfo(packageName, 0)
            true
        } catch (_: Exception) {
            false
        }
    }
}

On Android 11+ this works only for packages visible to your app, which is why the <queries> list matters.

7.2 Open “Install unknown apps” page
Kotlin
class AndroidSettingsNavigator(
    private val context: Context
) : SettingsNavigator {

    override fun openUnknownAppsSettings(packageName: String) {
        val intent = Intent(
            Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES,
            Uri.parse("package:$packageName")
        ).apply {
            addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
        }
        context.startActivity(intent)
    }

    override fun openPlayProtectInstructions() {
        val intent = Intent(Intent.ACTION_VIEW).apply {
            data = Uri.parse("https://support.google.com/googleplay/answer/2812853")
            addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
        }
        context.startActivity(intent)
    }
}

The key part is ACTION_MANAGE_UNKNOWN_APP_SOURCES, which is the official Android settings action for managing unknown app sources. 
Android Developers
